# MyTerra Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build MyTerra, a demo internet-provider customer portal: login, plan + usage chart, fake top-up, and support tickets.

**Architecture:** A FastAPI backend in `backend/` keeps fake users, plans and tickets in memory and exposes a JSON API under `/api`. An Angular app in `frontend/` calls that API, stores the login token, and shows three pages: Login, Dashboard (plan, balance, top-up, usage chart), Support (tickets).

**Tech Stack:** Python 3.12, FastAPI, uvicorn, pytest, httpx · Angular (latest CLI, standalone components), Chart.js

**Spec:** `docs/superpowers/specs/2026-10-29-myterra-design.md`

## Global Constraints

- All API routes start with `/api`. Backend runs on `http://localhost:8000`, frontend on `http://localhost:4200`; CORS allows `http://localhost:4200`.
- Protected routes need `Authorization: Bearer <token>`; missing/unknown token → `401` with `{"detail": "Not authenticated"}`.
- Demo users: `demo@myterra.app` / `demo1234` → plan "Fiber 50 GB", 50 GB, $20/month, balance 5.00. `sara@myterra.app` / `sara1234` → "Fiber 100 GB", 100 GB, $30/month, balance 12.50.
- Ticket status is one of `open`, `in_progress`, `resolved`; new tickets are `open`.
- Top-up: `0 < amount <= 500`, else `422`.
- Ticket: `subject` 1–100 chars, `message` 1–1000 chars (after trimming), else `422`.
- No real payments, no database, no signup.

## Review Focus

1. **Stale token after backend restart** — tokens live in memory, so a restart makes the saved token invalid; the frontend must send the user back to Login on any `401`, not show a broken page. (Task 6 test)
2. **Bad top-up input** — empty, negative, `0`, `abc`, or `100000` must show a clear message, never change the balance. (Task 4 + Task 7 tests)
3. **Double submit** — clicking Top up or Send twice quickly must not double-charge or create two tickets; buttons disable while the request runs. (Task 7 + Task 8 tests)
4. **Whitespace-only ticket** — `"   "` as subject or message is rejected like empty. (Task 5 test)
5. **Users see only their own data** — Sara must never see the demo user's tickets. (Task 5 test)
